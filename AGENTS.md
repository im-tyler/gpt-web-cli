# gpt-web-cli

`chatgpt-web` — CLI for driving ChatGPT from a terminal agent. Repo: `Tyler/gpt-web-cli` (Forgejo) with public GitHub mirror `im-tyler/gpt-web-cli` (remote `github`). Bin is npm-linked globally (`~/.local/bin/chatgpt-web`).

## Commands

- `start "prompt"` -> prints job id, returns immediately; `--file <path>` (repeatable) attaches files
- `send <id> "text"` -> follow-up in the same conversation; `--file` works here too
- `resume <id>` -> retry a failed assistant turn in standard ChatGPT (clicks the thread's own Retry control). NEVER clicks "Use Work": when the Work interstitial gates a conversation, sends/resume fail fast with that explanation — recover by starting a new chat. The interstitial's Retry is inert underneath (verified 2026-09-12); the backend wedges the thread into Work mode.
- `wait <id> [secs]` -> blocks, prints reply, exit 1 on error (default 600s); `--stream` prints as it grows (a sequence of labelled revisions, not necessarily a prefix of the final reply); `--turn <turnId>` pins a generation (a wait never answers a newer turn's reply silently); `--json` prints a structured final result (not combinable with `--stream`)
- `list`, `status`, `chats` (account threads via `/backend-api/conversations`, not CLI jobs), `login`
- `chats --delete <id>... | --delete --all --yes` -> hide conversations via `PATCH /backend-api/conversation/{id}` `{is_visible:false}`. Destructive deletes refuse on any listing error/cap, unknown id, or a conversation with a running turn; `--all` additionally requires `--yes` and a complete (uncapped) listing. Recovery terms are the service's — check Settings > Deleted chats. The old `PATCH /backend-api/conversation?id=` form returns 405 since ~2026-09 (verified 2026-09-17).

## Agent-mode threads (browser-research prompts)

Browse/research-heavy prompts (audits, "check github", file-producing tasks) route to ChatGPT agent mode: server-side `web.run`/`container.exec` tools, `async_status` numeric on the conversation (`3` running, `4` stopped; null observed mid-flight). Consequences learned live 2026-09-17:

- `start`/`send` observation often fails ("prompt was not observed as a new user message") because the agent DOM differs — the send still lands; the chat is created and the task runs. Check `~/.chatgpt-web/jobs/<id>.json` for the `url`, then poll `/backend-api/conversation/{id}` (`async_status`, `update_time`, mapping node count) instead of `wait`.
- Agent tasks can stop mid-research at their step budget (async 4, no deliverable, last message mid-thought). Recovery: `send <job-id> "You completed the research but never delivered the report. Please now write the complete ... to a single .md file."` — re-engages the same agent run.
- Deliverables are `sandbox:/mnt/data/*.md` links. If a sidebar file card appears, `files`/`download` work; often it does not — then reconstruct from the conversation JSON: the agent writes files via heredocs, so `code`-type messages contain `cat > path <<'MARK'` chunks; extract payload per marker, concatenate in create_time order, run any assembler script locally (patch `/mnt/data` paths).
- `files <chat-id>` / `download <chat-id> [n|all] [outdir]` -> conversation file artifacts
- `dot` -> bind + status of the account's dot; `dot "message"` -> send one paced, capped message into the dot thread; `dot --poll [--json]` -> messages since last poll (advances the watermark); `dot --context [n] [--json]` -> last n messages, 1..32 (the API 422s above 32; watermark untouched); `dot --reset` -> forget the binding. There is NO `wait` for dots: the dot replies on its own horizon (minutes to hours), so poll instead. A dot send is verified API-only (a NEW message id authored by this account with the exact authored text — the old DOM self-row fallback is gone) and is recorded as a `kind: "dot-send"` store generation whose `done` means *sent*, not *replied*; `send`/`resume`/`wait` refuse those records. `--file` is not supported yet (uploads refuse without a fixture-backed card-state profile).

## Dot threads (v0.6, verified 2026-10-03)

A dot conversation is NOT a `/c/<id>` thread. `/backend-api/conversation/<id>` returns 404 and the thread never appears in `/backend-api/conversations` — the Sept agent-mode polling advice does not apply. The dot surface is a **messaging room**:

- Discovery: `chatgpt.com/dots` redirects to `/dots/<dot-id>`; the room is the single `type:"DM"`, `app_source:"chatgpt:messaging"` entry in `GET /backend-api/messaging/rooms`. The binding (roomId, dotId, myId, watermark) lives in `~/.chatgpt-web/dot.json`, written only under the `dot` lock. Exactly one dot is tracked; multiple DM rooms refuse with the list.
- Reads: `GET /backend-api/messaging/rooms/<roomId>/messages?limit=100` (bearer, from a chatgpt.com page). Items: `{id, created_at, account_user_id, content.text}` — **authorship is `account_user_id`** (`user-…` = you, `calpico-member-…` = the dot); the `role` field is "user" on BOTH sides and must not be trusted.
- Sends: page composer on `/dots/<dot-id>` — the composer selectors are standard but the submit button is `button[aria-label="Send"]`, NOT `#composer-submit-button` (which does not exist on this surface). The transcript renders NO `[data-message-author-role]` nodes; own messages are `.message-row.self`. `data-message-id` on those nodes is the ROOM id on every node — useless as a message identity.
- Watermark (v2, 2026-10-06): `{v: 2, t, ids}` — membership is decided by ID (ids already counted are old), `t` is only a coarse backfill floor (the server returns created_at with varying sub-second precision between fetches, so exact time equality misclassifies the just-sent message — observed live 2026-10-03). The checkpoint RETAINS delivered ids (bounded, currently 512): a send merges its accepted id WITHOUT advancing `t`, so unread messages older than the send survive for the next poll (the v1 send-to-tip watermark silently dropped them). Poll delivery is at-least-once (a crash after stdout but before the checkpoint commit can replay a message). A full 32-message page with no checkpoint overlap refuses (`DOT_WINDOW_TRUNCATED`) rather than silently truncating history — read via `--context`, then `dot --reset` to rebaseline. True pagination needs the real cursor schema; do not guess one.
- Caps: a dot send is admitted like `send` (tab slot, daily turn cap, `lastSendAt` gap, send lock) but never counts against the new-chat cap — the thread already exists. It now reserves a real store generation (`kind: "dot-send"`) inside the admission transaction, so the slot is visible to concurrent admissions and a dead CLI process is filed by the startup lease/reaper. Reads (`dot`, `--poll`, `--context`) are free like `chats`, and every dot operation (including discovery) serializes under the `dot-operation` lock with the binding re-read after acquisition. Dot conversations don't count toward ChatGPT usage limits; Work/Codex tasks the dot starts do.
- No notifications for dot commands (they are synchronous); no `--file` yet (the dot composer's attachment UI is unmapped; any leftover attachment refuses the send).

## Web UI change 2026-10-04 (v0.6.2 fix, verified live)

The main chat surface converged to the dot-surface markup shape. On chatgpt.com (Chrome 154 era):

- Submit button is `button[aria-label="Send"]` — NO `#composer-submit-button`, NO `data-testid="send-button"`. `SUBMIT_SEL` now carries all three. The guarded submit requires a UNIQUE VISIBLE composer and a unique visible enabled Send button (`.first()`/`querySelector()` could grab a hidden template element).
- Transcripts render ZERO `[data-message-author-role]` / `data-message-id` nodes (main chats, not just dots). Consequences, all fixed API-first (2026-10-06 audit round):
  - `waitForReply` never scrapes the DOM. It polls `/backend-api/conversation/{id}` for the LAST user-facing assistant message after the accepted user message (tool/analysis channels excluded by recipient/content_type), and completion REQUIRES `status === 'finished_successfully'` AND `end_turn === true` (legacy no-channel terminal answers excepted). An intermediate "finished" message without `end_turn` no longer ends the wait, and the old text-silence quiet-period fallback is gone entirely — there is no text-silence completion. Partials fire from the growing API text.
  - Prompt acceptance matches a NEW user-message ID (the API baseline of `allUserIds` captured inside the send critical section, before the click) plus EXACT authored text (`canonicalPrompt` normalizes line endings only — no whitespace collapsing). STORED text is compared through `storedPromptText` (audit-core.mjs), the fixture-tested autolink adapter: the backend stores a bare URL as `[url](url)` (fixture 2026-10-07, smoke thread 6ac447ea…, message d4bbe119… — every other byte identical), and exactly self-labeled links (label === target) revert before the strict compare; distinct-label links and unprovable shapes (parens in the target) stay strict — a refusal, never a false accept. The authored side is never rewritten; `samePrompt` itself stays link-strict. Applied at `findAcceptedUser` and resume's pre-click authorization. The dot room's `content.text` has NO fixture yet — dot acceptance stays exact (if a dot URL send ever files unverified, capture the fixture there before extending the adapter). The DOM `priorIds` snapshot was always `[]` on this UI and could re-accept an older identical prompt; it is gone. Strict comparison may still refuse an unmapped storage transform — preferable to accepting a different prompt. After a possible click there is NEVER an automatic re-send; `ACCEPTANCE_UNKNOWN` means inspect first.
  - The pre-click submission guard (main + dot) compares the composer's rendered text WHITESPACE-FLATTENED ON BOTH SIDES against the prompt: the 2026-10 contenteditable renders a paragraph break at the autolink boundary (held `audit \nhttps://…` for authored `audit https://…`, live 2026-10-07 — the break is NOT stored, storage keeps the space), so innerText block boundaries are rendering, not content. Token identity is what the guard protects — a different-token draft clobber still refuses — and authored identity is proven post-click by API acceptance. Both sides flatten, so multi-line prompts compare correctly (the Oct-4 flattening compared flattened held text against a line-preserved prompt; no multi-line prompt could ever match it).
- Still dead / unmapped on the new UI (not blocking start/send/wait): `resume`'s `regenerate-thread-error-button` (resume refuses with `RESUME_UNSUPPORTED_UI` before touching the conversation), the attachment card STATE profile (`--file` uploads error "attachment state unrecognized / UPLOAD_UNSUPPORTED_UI" until a fixture-backed profile maps card attributes; found-but-unparseable chips refuse instead of guessing ready), `replyAfterUser` (removed). Attachment PRESENCE at the click boundary is checked inside the submit guard via the composer's attachment slot: live fixture 2026-10-06 (main-chat surface) — the composer FORM contains a `ComposerLayoutAttachments-*` container with ZERO element children when empty (structural empty-state sentinel; verified-empty, not "zero selector matches"); a populated slot, or legacy chips in scope, refuses a no-file send. The live surface also renders exactly ONE visible composer (`div[contenteditable="true"]`, no `#prompt-textarea` id) per page at rest, which the unique-visible submit guard relies on.
- Drafts persist server-side on the new-chat surface; `typePrompt`'s select-all + insertText replaces them (verified).

## Model picker + power slider (v0.6.3, verified live 2026-10-05)

The model popover carries TWO controls: the named-model radios AND a thinking-power slider (the way to reach GPT-6 Pro).

- Trigger: `button[aria-label="Select ChatGPT model"]` (no testid; the old testid candidates are dead). The button caption can read "Pro" or "Thinking effort" — never trust it for state.
- Slider row: `[data-reasoning-slider="true"]` (= `[role="menuitem"][aria-label="Power"]`). No `aria-valuenow`: the value is in its aria-describedby text, `"Pro, 5 of 5."` → stop name + position (runner fn `parseSliderDesc`). The `Select model` menuitem shows the effective label ("6 Pro" at stop 5).
- Stops 2026-10-05: 1 Instant, 2 Medium, 3 High, 4 Extra High, 5 Pro (effective "6 Pro", with radio "Latest"). Adjust = focus() the row, then ArrowLeft/Right (one stop per press). NEVER click the track — pointer-down drags the value.
- The slider is an **account-wide default**: set once, every composer inherits it — including fresh chats the runner starts. `start`/`send` therefore need no model logic; they run at whatever the slider last held. The ENTIRE `model` operation (list or set) runs under the `send` lock, taken before the model command's page exists, so a picker change never reorders against a live send/dot-send/retry. A plain `model` listing is READ-ONLY: it prints the named radios and the CURRENT readable slider stop only (no slider walk — the walk temporarily moves the account default; stop names are discovered only while setting). Setting walks with snapshot/restore fencing and reports restoration failures instead of silently leaving a changed default.
- `model` lists radios + a `slider (thinking power):` section carrying the current stop; other stop names appear when setting one. `model <fragment>` (multi-word fragments ok: `model 6 pro`) matches radios OR stops by substring on name + effective label ("6 pro" → Pro stop; "pro" hits the same stop once via both labels; "high" is ambiguous High|Extra High). Setting a stop moves by arrow presses, then re-opens the popover to verify the read-back. Slider movement dispatches synthetic KeyboardEvents on the row — CDP `page.keyboard` presses get ignored in stretches while the radix popover settles, and the position can drift after a read (animation lag), so every movement loop waits for two consecutive reads agreeing on the FULL state (name, position, total, effective label — `sliderEqual`; unsettled throws). E2E verified 2026-10-05: `model 6 pro` → send → conversation JSON `model_slug: "gpt-6-pro"`.
- The 2026-09-09 filechooser crash class (unhandled `waitForEvent` rejection killing the runner): known wait sites carry inline catches, and the worker entry (`runner-entry.mjs`, the only place process-fatal handlers install) fences fatals — abort the runner first (no later browser mutations), file the failure into the active turn, exit non-zero, with a forced-exit watchdog that never touches the Chrome daemon. Importing `runner.mjs` is inert: no handlers, no validation exits.

## Upload + streaming notes (v0.3)

- Uploads: click `[data-testid="composer-plus-btn"]` -> popover -> `getByText(/upload from computer/i)` -> `page.waitForEvent('filechooser')` -> `setFiles`. Match by regex, NOT exact text (popover markup varies).
- NEVER leave a pending `waitForEvent` promise unawaited after an early throw — attach a sibling `.catch(() => {})` immediately, or the delayed rejection kills the whole runner as an unhandled rejection (job reads "runner died").
- First send on a fresh chat navigates `/` -> `/c/<id>` and the message list REMOUNTS — assistant-message count flickers 0->1->0. Response-start detection requires 2 consecutive positive sightings, never break-then-recheck.
- Job statuses: `running` -> `streaming` (partial reply written every >=2s) -> `done`. Admission/reapStale/send-guard all treat `streaming` as busy.

## File download notes

Agent-chat files have no stable listing API (conversation endpoint 404s; `/interpreter/download` needs message_id + sandbox_path). Working approach: click each `[data-testid="library-file-icon"]` (reload the page between clicks — the estuary fetch is cache-swallowed on repeat clicks in one session), intercept `GET /backend-api/estuary/content?id=<file_id>&fn=<name>` and read `response.body()` IMMEDIATELY (bodies die on next navigation). 4 sidebar icons may be 2-4 unique files; dedupe by id.

## Concurrency (v0.5)

Multiple agents can use the CLI at once. Up to `CHATGPT_WEB_MAX_TABS` concurrent turns (default 2), each in its own tab: `start`/`send` admit while `runningJobs().length < maxTabs`. Every command invocation creates its own page (`withPage` → `context.newPage()`, closed in `finally`) — no command ever touches another turn's tab. The send phase (gap wait → settle → upload → type → click) runs under a cross-process filesystem lock (`~/.chatgpt-web/locks/send.lock`, kernel flock, permanent lock file); the min-gap is measured between SENDS (`state.lastSendAt`), not turn ends. Response waits happen in parallel outside the lock. `model` operations share the same `send` lock. Caps remain global per account; the limits check + `recordTurn` run under `locks/state.lock` so concurrent starts can't lose counts. Admission check has a small TOCTOU window — two simultaneous starts can both pass; harmless at cap 2.

## Locks (v0.7.0)

All cross-process locks are kernel flocks on PERMANENT files in `~/.chatgpt-web/locks/` (`*.flock`). Never delete or recreate them — unlinking a live lock file lets different processes lock different inodes of the same name; the kernel releases a flock when its holder dies, so there is nothing to clean up. `browser-visibility` is taken SHARED by ordinary page lifetimes and EXCLUSIVE by `login` (so nothing's hide timer fights the login window); `daemon-startup` serializes the whole daemon ensure/reuse decision INCLUDING identity publication; `dot-operation` serializes every dot read/send; `worker-<turnId>` is held by a detached worker for its whole run.

## Architecture (do not regress this)

One long-lived **plain Chrome** daemon (`--remote-debugging-port=9777`, real keychain, zero automation flags) is spawned on demand; all commands drive it over CDP via playwright-core `connectOverCDP({ noDefaults: true })` (Chrome 152+ rejects `Browser.setDownloadBehavior` on the default profile). If `/json` has no `page` target, `PUT /json/new?about:blank` first. Login session lives inside that process.

**NEVER** run Playwright `launchPersistentContext` against the profile dir (`~/.chatgpt-web/profile`). Playwright injects `--use-mock-keychain`; Chrome then cannot decrypt the session cookies written by real Chrome and silently DELETES them (destroyed a live session this way once, 2026-09-09). No UA spoofing either — it is real Chrome; spoofing breaks Cloudflare.

## Operational rules

- The daemon Chrome process must stay alive. Windowed: minimize is fine; Cmd+Q = session home gone. `CHATGPT_WEB_HEADLESS=1` does **not** pass `--headless` (Cloudflare challenges that). It spawns the same headed Chrome and hides the process via System Events (`visible=false`). Login unhides (and opts out of auto-hide for its whole run). Never spoof UA or use stealth patches.
- Up to `CHATGPT_WEB_MAX_TABS` concurrent turns (default 2), one tab each. Sends are serialized + paced globally (send lock + `lastSendAt` gap); response waits overlap. Do not raise the gap-bypass or tabs past 3 — interleaved machine-cadence tabs are a flag tell.
- Jobs: `~/.chatgpt-web/jobs/<id>.json` (id, kind, status, prompt, reply, url, history, pid, turnId, acceptedUserId/assistantMessageId/submissionState provenance). Crashed runners self-heal to `error` via pid check. Corrupt job/state/dot records THROW (surfaced with their filename) instead of reading as absent — an invisible "running" job used to free a tab slot and a corrupt state.json used to reset the caps.
- chatgpt.com renders a logged-out SSR shell with login buttons for a few seconds after navigation — page classification must wait for settle (`classifyPage`), never judge on first paint.
- Response completion (API-first, 2026-10 UI): the last user-facing assistant message after the accepted prompt is `finished_successfully` AND `end_turn` — there is no DOM/text-silence completion heuristic anymore.
- Env: `CHATGPT_WEB_HOME`, `CHATGPT_WEB_TIMEOUT` (reply deadline per turn in secs, default 300 — it bounds the reply wait, not the whole end-to-end turn), `CHATGPT_WEB_CDP_PORT` (default 9777), `CHATGPT_WEB_CHROME` (binary path), `CHATGPT_WEB_HEADLESS=1` (hide headed window; never `--headless`), `CHATGPT_WEB_MAX_TABS` (concurrent turns, default 2, bound 1..16), `CHATGPT_WEB_MAX_TURNS_DAY` (default 100), `CHATGPT_WEB_MAX_NEW_CHATS` (per hour, default 6), `CHATGPT_WEB_MIN_GAP` (secs between sends, default 8, bound 0..86400), `CHATGPT_WEB_NOTIFY=0` disables notifications. Explicit invalid values fail the command (they used to silently fall back to defaults); these are HOME-local resource bounds, not account-wide service limits. Caps count ADMISSIONS (charged before the worker proves the send), not confirmed submissions.

## Pacing + caps (flag-risk reduction, v0.2)

Behavioral camouflage is the priority — NOT fingerprint spoofing (real Chrome + zero flags already; spoofing would create tells). Built in:

- Randomized human pacing: 8-16s enforced gap between sends (`CHATGPT_WEB_MIN_GAP`, measured from `state.lastSendAt` under the send lock), 1.5-4s settle before typing, jittered poll intervals (~0.6-1.3s).
- Caps in `~/.chatgpt-web/state.json`: max 100 turns/day (`CHATGPT_WEB_MAX_TURNS_DAY`), max 6 new conversations/hour (`CHATGPT_WEB_MAX_NEW_CHATS`) — `start`/`send` refuse with exit 1 when hit; prefer `send` follow-ups over new chats.
- macOS notification on every turn end/error (`CHATGPT_WEB_NOTIFY=0` to disable).
- `status` command: daemon, session, usage vs caps, running jobs.
- Account hygiene matters more than code: automation runs on a secondary account, never a business one.
